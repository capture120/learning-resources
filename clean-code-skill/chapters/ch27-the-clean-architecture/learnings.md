# Chapter 27: The Clean Architecture

Architectures like Hexagonal (Ports and Adapters), DCI, and BCE all share one objective: separation of concerns through layers, with business rules isolated from interfaces. The Clean Architecture is an attempt to integrate them into a single actionable idea — concentric circles of software governed by one overriding rule: source code dependencies point only inward, toward higher-level policies. Follow that rule and the system becomes intrinsically testable and its details (database, web, frameworks) become replaceable.

## Properties a Clean Architecture must deliver

Any architecture in this family produces systems that are:

- **Independent of frameworks.** Frameworks are tools to use, not constraints to cram your system into. The architecture must not depend on the existence of some feature-laden library.
- **Testable.** Business rules can be tested without the UI, database, web server, or any other external element.
- **Independent of UI.** The UI can change (e.g., web UI swapped for console UI) without touching business rules.
- **Independent of database.** Swap Oracle for Mongo, Bigtable, or CouchDB; business rules are not bound to the database.
- **Independent of any external agency.** Business rules know nothing at all about interfaces to the outside world.

## The Dependency Rule

**"Source code dependencies must only point inward, toward higher-level policies."** This is the overriding rule that makes the architecture work. Concentric circles represent areas of software: outer circles are mechanisms, inner circles are policies; the further in, the higher level the software. Nothing in an inner circle may know anything about an outer circle — no name declared in an outer circle (function, class, variable, any named entity) may be mentioned by inner-circle code. Data formats declared in an outer circle, especially formats generated by a framework, should not be used by an inner circle. Nothing in an outer circle should impact the inner circles.

## Entities

Entities encapsulate enterprise-wide critical business rules — the most general, highest-level rules, usable by many applications across the enterprise. Form doesn't matter (object with methods, or data structures plus functions). If you have only a single application, entities are its business objects. Entities are the least likely to change when something external changes: no change to page navigation, security, or any operational change to a particular application should affect this layer.

## Use Cases

This layer contains application-specific business rules: it encapsulates and implements all use cases of the system, orchestrating the flow of data to and from the entities and directing entities to apply their critical business rules. Changes here should not affect entities, and changes to externalities (database, UI, frameworks) should not affect this layer. But changes to the operation of the application *will* affect use cases — if a use case's details change, code in this layer changes. That's expected and correct.

## Interface Adapters

A layer of adapters that convert data between the format most convenient for use cases/entities and the format most convenient for external agencies (database, web, external services). The whole MVC architecture of a GUI lives here — presenters, views, and controllers — with models likely just plain data structures passed between them and the use cases. If it's a SQL database, all SQL is restricted to this layer; no code inward of this circle knows anything at all about the database.

## Frameworks and Drivers

The outermost layer: frameworks and tools such as the database and the web framework. You write little code here beyond glue that communicates inward. **"This layer is where all the details go. The Web is a detail. The database is a detail."** Keep details on the outside, where they can do little harm.

## Only Four Circles?

The four circles are schematic, not a law — you may need more. There is no rule that you must have exactly four. What *always* applies is the Dependency Rule: dependencies point inward, abstraction and policy increase as you move inward, the outermost circle is low-level concrete detail, the innermost is the most general and highest level.

## Crossing Boundaries

Flow of control may run opposite to the dependency direction (e.g., control flows controller → use case → presenter, yet all source dependencies must point inward to the use case). This apparent contradiction is usually resolved with the **Dependency Inversion Principle (DIP)**: arrange interfaces and inheritance so source code dependencies oppose the flow of control at the boundary. The use case must not call the presenter directly (an inner circle naming an outer one); instead the use case calls an interface declared in the inner circle (a **Use Case Output Port**) and the presenter in the outer circle implements it. Dynamic polymorphism lets you conform to the Dependency Rule no matter which direction control flows.

## What Data Crosses the Boundaries

Pass isolated, simple data structures across boundaries: basic structs, simple DTOs, function arguments, hash maps, or plain objects — the form doesn't matter, the isolation does. Don't cheat by passing entities or database rows. A framework's "row structure" returned from a query must not be passed inward — that forces an inner circle to know about an outer one. **When data crosses a boundary, it is always in the form most convenient for the inner circle.**

## In practice

- Before adding an import or reference, check direction: business rules must never name UI, database, framework, or external-service code.
- Put enterprise-wide rules in entities; application-specific orchestration in use cases; format conversion in interface adapters; only glue code in the frameworks layer.
- Keep all SQL (and all database knowledge) in the interface-adapter layer or further out.
- When an inner layer must trigger outer-layer behavior, define an interface (output port) in the inner layer and implement it in the outer layer (DIP).
- Pass plain data structures (DTOs, structs, arguments) across boundaries, shaped for the inner circle; never pass entities or framework-generated rows inward.
- Treat frameworks as tools you call, not platforms you inherit from; keep the Web and the database replaceable details.
- Verify the architecture by testability: business rules should be testable with no UI, database, or web server present.
- Add or remove circles as needed, but never break the inward-only dependency direction.
