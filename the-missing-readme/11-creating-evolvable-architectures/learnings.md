# Chapter 11: Creating Evolvable Architectures

Requirements volatility — changing customer demands — is unavoidable, so software must be built to change; left unmanaged, changing requirements cause instability and derail development. Managers address volatility with iterative development processes like Agile; engineers do their part by building evolvable architectures, which accommodate changing requirements by eschewing complexity, the enemy of evolvability. Achieving simplicity takes conscious effort: without it, code grows tangled and complex, so this chapter defines complexity, gives design principles that reduce it, and translates those principles into concrete API and data-layer practices.

## Core Concepts

### Understanding Complexity
John Ousterhout (in *A Philosophy of Software Design*) defines complexity as "anything related to the structure of a system that makes it hard to understand and modify the system." Complex systems have two characteristics per Ousterhout — high dependency and high obscurity — plus a third the authors add: high inertia.

- **High dependency**: code relies on other code's API or behavior. Dependency is unavoidable and even desirable, but every new connection and assumption makes code harder to change. High-dependency systems suffer *tight coupling* (modules depending heavily on one another) and *change amplification* (a single change forces modifications in dependencies too). Thoughtful API design and restrained use of abstraction minimize both.
- **High obscurity**: developers can't predict a change's side effects, how code behaves, or where changes need to go. Obscure code takes longer to learn and gets broken inadvertently. Symptoms: *god objects* that "know" too much, global state that encourages side effects, excessive indirection that hides what code does, and *action at a distance* (behavior affected from distant parts of the program). APIs with clear contracts and standard patterns reduce obscurity.
- **High inertia**: software's tendency to stay in use. Quick-experiment code that's easily discarded has low inertia; a service powering a dozen business-critical applications has high inertia. Complexity's cost accrues over time, so simplify high-inertia, high-change systems; low-inertia or low-change systems can be left complex, as long as you discard them or leave them alone.

Complexity cannot always be eliminated — but you can choose where to put it. Backward-compatible changes make code simpler to use but more complicated to implement. Layers of indirection that decouple subsystems reduce dependency but increase obscurity. Be thoughtful about when, where, and how you manage complexity.

### Design for Evolvability
Faced with unknown future requirements, engineers usually pick one of two tactics: guess what they'll need, or build abstractions as an escape hatch to make later changes easier. Don't play this game — both approaches lead to complexity. Instead, keep it simple (KISS: "keep it simple, stupid"). Simple code lets you add complexity later, when the need is clear and the change unavoidable. The easiest way to keep code simple is to avoid writing it at all (YAGNI). When you do write code, apply the principle of least astonishment and encapsulation.

### You Ain't Gonna Need It (YAGNI)
Don't build things you don't need. YAGNI violations happen when developers get excited, fixated, or worried about some aspect of their code. Predicting future needs is hard; every wrong guess is wasted effort, and after the initial waste the unneeded code bogs things down — it must be maintained, understood, built, and tested. Three habits avoid unnecessary development:

- **Avoid premature optimization.** The classic scenario: a developer spots code that could be faster or more scalable, adds complex logic or architectural layers (caches, sharded databases, queues) before the code has shipped or anyone has used it, then discovers the optimization wasn't needed. Removing optimization never happens; complexity accrues. Most performance and scalability improvements carry a high complexity cost — a cache is fast, but it can become inconsistent with the underlying data.
- **Avoid unnecessarily flexible abstractions** — plugin architectures, wrapper interfaces, and generic data structures like key-value pairs. Developers think they can easily adjust if a new requirement pops up, but abstraction has a cost: it boxes implementations into rigid boundaries you end up fighting, and flexibility makes code harder to read and understand. Wrapping divergent implementations forces a bad choice: a union of all features (no single implementation supports every method) or an intersection (too limited to be useful). You're better off using an implementation directly and refactoring later if you actually need another one.
- **Avoid product features that aren't needed for a minimum viable product (MVP)** — the bare-minimum feature set you need to get user feedback. Developers talk themselves into the cool-feature pitfall: they mistake their own usage for what most users want, think the feature will be easy to add, or just think it's neat. Every feature takes time to build and maintain, and you don't know if it will actually be useful. An MVP keeps you honest and lets you test an idea without a full-fledged implementation.

The best way to keep code flexible is simply to have less of it. For everything you build, ask what is absolutely necessary and throw away the rest — a technique called *Muntzing* that keeps software trim and adaptable.

YAGNI has caveats. As experience grows, you get better at predicting when flexibility and optimization are genuinely necessary. In the meantime, place interface shims where you suspect optimizations can be inserted, but don't actually implement them — e.g., give a new file format a header that specifies the encoding while only implementing the uncompressed encoding; compression can be added later, and the header makes it easy for new code to read older files.

### Principle of Least Astonishment
Don't surprise users: build features that behave the way users first expect; features with a high learning curve or strange behavior frustrate them. Don't surprise developers either: surprising code is obscure, and obscurity causes complexity. Eliminate surprises by keeping code specific, avoiding implicit knowledge, and using standard libraries and patterns.

*Implicit knowledge* is anything nonobvious a developer must know to use an API that isn't part of the API itself. APIs requiring implicit knowledge surprise developers, causing bugs and a high learning curve. Two common violations:

- **Hidden ordering requirements**: actions must take place in a specific sequence — method A must be called before method B — but the API lets you call B first, surprising the developer with a runtime error. Documenting an ordering requirement is good, but not having one is better. Fixes: have methods invoke their prerequisite submethods (check state and initialize internally), combine the methods into one, use the builder pattern, or use the type system so the method only operates on already-prepared types. At minimum, name the method so it hints at the requirement. Counterintuitively, short method and variable names increase cognitive load — specific, longer names are more descriptive and easier to understand.
- **Hidden argument requirements**: the signature implies a wider range of valid inputs than the method actually accepts — e.g., accepting an `int` while only allowing 1–10, or requiring that a certain value field be set inside a plain JSON object. Make argument requirements specific and visible: use specific types that accurately capture constraints; when using flexible types like JSON, consider JSON Schema to describe the expected object; at the least, advertise argument requirements in documentation when they can't be made programmatically visible.

Finally, use standard libraries and development patterns. Implementing your own square root method is surprising; using the language's built-in one is not. The same rule applies to development patterns: use idiomatic code style and idiomatic patterns.

### Encapsulate Domain Knowledge
Software changes as business requirements change, so group software by business domain — accounting, billing, shipping, and so on. Mapping software components to business domains keeps code changes focused and clean.

Encapsulated domains naturally gravitate toward *high cohesion* (methods, variables, and classes that relate to one another live near each other in modules or packages) and *low coupling* (decoupled code is self-contained; a change to its logic doesn't require changes to other components). Highly cohesive, loosely coupled software is more evolvable because changes have a smaller "blast radius."

Contrast this with layering by technical domain (frontend, middle tier, backend — all UI code in one place, all object persistence in another). Layering works great within a single business domain but grows messy as businesses grow: separate teams form around each tier, increasing coordination cost because every business logic change slices through all tiers, and shared horizontal layers make it too easy for developers to mix business logic between domains, leading to complex code.

Identifying domain boundaries and encapsulating domain knowledge is as much art as science. *Domain-Driven Design (DDD)* is an entire architectural approach defining an extensive set of concepts and practices to map business concepts to software. Full-blown DDD is necessary only for the most complex situations, but familiarity with it helps you make better design decisions.

### Evolvable APIs
APIs — the shared interfaces between code — must change as requirements change. Changing an API is easy to do but hard to do right: many small, rational changes can lead to a sprawling mess, and a minor change can completely break compatibility. If an API changes incompatibly, clients break — and the breakage may not be immediately obvious, especially when it happens at runtime rather than during compilation. APIs that are small, clearly defined, compatible, and versioned are easier to use and evolve.

**Keep APIs small.** Small APIs are easier to understand and evolve; larger APIs put more cognitive load on developers and create more code to document, support, debug, and maintain. Every new method or field grows the API and locks you further into a specific usage pattern. Apply the YAGNI philosophy: only add API methods or fields that are immediately needed; when creating an API data model, only add methods you need at the time; when bootstrapping an API with a framework or generator tool, eliminate fields or methods you're not using. Give methods with many fields sensible defaults so developers can focus on relevant fields knowing they'll inherit defaults for the rest — defaults make large APIs feel small.

**Expose well-defined service APIs.** Evolvable systems have clearly defined request and response schemas that are versioned and have clear compatibility contracts. Publish schema definitions so they can be used to automatically test both client and server code. Use standard tools — an *interface definition language (IDL)*: OpenAPI is common for RESTful services; non-REST services use Protocol Buffers, Thrift, or similar. A well-defined service declares its schemas, request and response methods, and exceptions; this makes compile-time validation easier and keeps clients, servers, and documentation in sync. IDL tooling includes code generators that convert service definitions to client and server code, generated documentation, test tools that produce stubs and mock data, and sometimes discoverability features (find services, learn who maintains them, see how they're used). Use your company's API definition framework if one is chosen — picking a "better" one requires too much interoperability work. If your company hand-rolls REST APIs and evolves JSON interfaces in code without a formal spec, OpenAPI is the best bet: it retrofits onto preexisting REST services without major migrations.

**Keep API changes compatible.** Compatibility lets client and server versions evolve independently. Two forms:
- *Forward-compatible* changes allow clients to use a new version of an API when invoking an older service version (a service running v1.0 that can receive calls from a v1.1 client is forward compatible).
- *Backward-compatible* changes mean new versions of the library or service don't require changes in older client code (code developed against v1.0 continues to compile and run with v1.1).

Adding a required field is backward-incompatible: old clients don't supply it, so the service can't parse their requests; removing the "required" constraint and handling absence preserves backward compatibility. Required fields are such an evolvability problem that they were removed from Protocol Buffers v3 — per its primary v2 author, "required" was "a horrible mistake"; remember, "Required is forever." Changing a field's wire type (e.g., int32 to sint32 in Protocol Buffers) can be both backward- and forward-incompatible because old and new sides encode the field differently and each fails to parse the other. The compatible path: add a new field for the new type and rename the old one as deprecated (renaming is safe when the field ordinal stays the same); the server handles both fields for as long as old clients are supported; once rolled out, monitor how often clients use the deprecated field and clean it up after clients upgrade or a deprecation schedule expires. These problems aren't unique to strongly typed systems — "simple" REST services hit them too whenever client and server content expectations diverge. And it's not just message fields: a change in message *semantics* — the logic of what happens when certain events transpire — can also be backward- or forward-incompatible.

**Version APIs.** Fully backward- and forward-compatible changes interoperate with all previous and future versions, but that's hard to maintain and creates cruft (like logic for handling deprecated fields); less stringent compatibility guarantees allow more radical changes. Eventually you'll need an incompatible change — requiring a new field, for example. Versioning means you introduce a new version when changes are made; old clients continue using the old version. Tracking versions also helps you communicate with customers — they can tell you what version they use, and you can market new features with a new version. Versions are usually managed with an API gateway or service mesh routing versioned requests to the appropriate service (v2 requests to a v2.X.X instance, v3 to v3.X.X); absent a gateway, clients invoke version-specific service hosts directly, or a single service instance runs multiple versions internally. Versioning has costs: older major versions must be maintained, bug fixes backported, and feature-to-version mappings tracked; lacking tooling, version management lands on engineers. Be pragmatic about methodology — semantic versioning is common, but many companies version APIs with dates or other numeric schemes, and version numbers can live in URI paths, query parameters, or HTTP Accept headers, each with trade-offs and strong opinions. Defer to your company's standard; if there isn't one, ask your manager and tech leads. Keep documentation versioned along with your APIs — developers on older versions need accurate docs, and it's confusing to reference documentation that doesn't match the API you're using; committing API documentation in the main code repository keeps docs and code in sync, since pull requests can update documentation as they change APIs and behavior. Versioning is most valuable when client code is hard to change: you usually have the least control over external (customer) clients, so customer-facing APIs are the most important to version. If your team controls both the service and the client, you might get away without internal API versioning.

### Evolvable Data
APIs are more ephemeral than persisted data: once client and server APIs are upgraded, the work is done, but data must keep evolving as applications change. Data evolution runs the gamut from simple schema changes (adding or removing a column) to rewriting records with new schemas, fixing corruption, rewriting to match new business logic, and massive migrations from one database to another. Three practices make data evolution manageable: isolate databases (so you only worry about a change's impact on your own application), use explicit schemas (so you're protected from reading or writing malformed data), and automate schema migrations (so schema changes are predictable).

**Isolate databases.** Shared databases — accessed by more than one application — are difficult to evolve and cause a loss of *autonomy*: a developer's or team's ability to make independent changes to the system. You won't be able to safely modify schemas, or even read and write, without worrying about how everyone else uses your database; the architecture grows brittle as schemas become an unofficial, deeply entrenched API. Shared databases cause many problems: applications grow to depend directly on each other's data; applications act as a control point for the data they serve, but with a shared database you can't apply business logic to raw data before serving it and can't easily redirect queries to a new data store during a migration when queries bypass your application; with multiple writers, the meaning (semantics) of data can diverge, making it harder for readers to reason about; application data isn't protected, so other applications might mutate it unexpectedly; schemas aren't isolated — one application's schema change can impact others; performance isn't isolated — one application overwhelming the database affects all the others; and in some cases security boundaries might be violated. By contrast, isolated databases have a single reader and writer, with all other traffic going through remote procedure calls — you only worry about your own application when making schema changes, and database performance is governed by your own usage. There are occasional cases where a shared database is valuable: when breaking up a monolith, sharing the database is a useful intermediate step before data is migrated to a new isolated database; and since managing many databases carries high operational cost, early on it might make sense to co-locate many databases on the same machines. But make sure any shared databases eventually get isolated and split up or replaced.

**Use schemas.** Schemaless data management became popular because rigid predefined columns and types — and the heavyweight processes for evolving them — are painful, and most modern datastores can store JSON-like objects without predeclared structure. But schemaless doesn't literally mean "no schema" (data would be unusable); it means an *implicit* schema that is supplied or inferred at read time. In practice, schemaless approaches cause significant data integrity and complexity problems. A strongly typed, schema-forward approach decreases the obscurity, and therefore the complexity, of your application; the short-term simplicity of schemaless usually isn't worth the obscurity trade-off. Like code, data is "write once, read many" — use schemas to make reads easier. You'd think no schema makes changes easier (just start or stop writing fields), but schemaless actually makes changes *harder* because you don't know what you're breaking as you evolve your data; data quickly becomes an unintelligible hodgepodge of different record types that developers, business analysts, and data scientists struggle to keep up with. Explicit schemas keep your application stable and your data usable: they let you sanity-check data as it's written, make parsing faster, help detect forward- and backward-incompatible changes, and tell data consumers what to expect. The rigidity of explicit schemas carries a cost — they can be difficult to change — but this is by design: schemas force you to slow down and think through how existing data will be migrated and how downstream users will be affected. Don't hide schemaless data inside schematized data — it's tempting to stuff a JSON string into a field called "data" or define a map of strings for arbitrary key-value pairs, but hiding schemaless data is self-defeating: you get all the pain of explicit schemas and none of the gain. Schemaless is warranted in some cases: when your primary goal is to move fast (before you know what you need, when you're iterating rapidly, or when old data has little to no value), when data is legitimately nonuniform (some records have fields others don't), or as a migration trick — temporarily flipping data from explicit to implicit schema to ease the transition to a new explicit schema.

**Automate schema migrations.** Changing a database's schema is dangerous: a minor tweak — adding an index or dropping a column — can cause the entire database or application to grind to a halt. Managing changes by manually executing DDL (database description language) commands directly on the database is error prone: schemas in different environments diverge, the state of the database becomes uncertain, no one knows who changed what when, and performance impacts are unclear. Error-prone changes plus the potential for major downtime is an explosive combination. Database schema management tools make changes less error prone by doing two things: forcing you to track the entire history of a schema, and giving you tools to migrate a schema from one version to another. The history is usually a series of files defining every change from the schema's initial creation to its current form; tracking DDL changes in files helps developers see how the schema evolved, version control shows who made which changes, when, and why, and pull requests afford schema reviews and linting. Migration tools (e.g., Liquibase, Flyway, Alembic; many ORMs ship schema migration managers) often track the current schema version in special metadata tables inside the database itself, and apply only the changesets not yet executed. Migrations are usually run by a database administrator; some teams automate execution through a commit hook or a web UI. Don't couple database and application lifecycles: tying schema migrations to application deployment is dangerous because schema changes are delicate and can have serious performance implications — separating them lets you control when schema changes go out. Use your company's existing migration tool if there is one; if not, work with the team to pick one. Once selected, use it for *all* changes — circumventing it negates the tool's benefit because reality diverges from what's tracked. More sophisticated database operations tools also exist: GitHub's gh-ost and Percona's pt-online-schema-change help DBAs run large schema changes without impacting performance; Skeema and Square's Shift provide versioning that lets you "diff" database schemas and automatically derive changes. Most migration tools support rollbacks, which undo a migration's changes — but rollbacks can only do so much: rolling back a column deletion recreates the column, but not the data that was stored in it. Backing up a table prior to deletion is prudent. Because these changes are permanent and large-scale, organizations often have specific subteams (DBAs, ops or SREs, or senior engineers familiar with the tools, performance implications, and application-specific concerns) responsible for ensuring they're done correctly — they're a great resource for understanding data storage nuances; learn from them.

**Maintain schema compatibility.** Data written to disk has the same compatibility problems as APIs: the reader and writer of the data can change independently — they might not be the same software and might not be on the same machine — and the data has a schema with field names and types, so changing schemas in a forward- or backward-incompatible way can break applications. Use schema compatibility checks to detect incompatible changes, and use data products to decouple internal and external schemas. Developers think databases are an implementation detail hidden from other systems; fully encapsulated databases are ideal but not often realized in practice. Even when a production database is hidden behind an application, the data is often exported to data warehouses — databases used for analytic and reporting purposes — via an extract-transform-load (ETL) pipeline that extracts data from production databases, transforms it, and loads it into the warehouse. ETL pipelines depend heavily on database schemas: simply dropping a column in a production database can cause the entire data pipeline to grind to a halt, and even when the pipeline survives, downstream users might use the field for reporting, machine learning models, or ad hoc queries. Other systems also depend on your schemas: change data capture (CDC) is an event-based architecture that converts insert, update, and delete operations into messages for downstream consumers (e.g., an insert into a "members" table triggers a message an email service uses to welcome the new user). Such messages are an implicit API, and backward-incompatible schema changes can break other services. Protect data warehouse pipelines and downstream users from breaking schema changes: validate that changes are safe before executing them in production, with compatibility checks done as early as possible — ideally at code commit time by inspecting database DDL statements — and by executing DDL statements plus integration tests in a preproduction integration testing environment to verify downstream systems don't break. You can also protect internal schemas by exporting a *data product* that explicitly decouples internal schemas from downstream users: data products map internal schemas to separate user-facing schemas, with the development team owning both the production database and the published data products. Separate data products — which might simply be database views — let teams maintain compatibility with data consumers without freezing their internal database schemas.

## Actionable Practices

The authors' own Do's and Don'ts:

- DO remember YAGNI: "You Ain't Gonna Need It."
- DO use standard libraries and development patterns.
- DO use an IDL to define your APIs.
- DO version external APIs and documentation.
- DO isolate application databases from each other.
- DO define explicit schemas for all your data.
- DO use migration tools to automate database schema management.
- DO maintain schema compatibility if downstream consumers use your data.
- DON'T build too many abstractions without purpose.
- DON'T write methods with hidden ordering or argument requirements.
- DON'T surprise other developers with exotic code.
- DON'T make incompatible API changes.
- DON'T be dogmatic about internal API versioning.
- DON'T embed schemaless data in string or byte fields.

Additional imperatives from the chapter:

- Build with simplicity in mind (KISS); add complexity later, when the need is clear and the change unavoidable.
- Don't guess future requirements and don't pre-build abstraction escape hatches.
- Build an MVP first; skip features not needed to get user feedback.
- Muntz your designs: for everything you build, ask what is absolutely necessary and throw away the rest.
- Where you suspect future optimization, place a cheap interface shim (e.g., an encoding header in a file format) but don't implement the feature yet.
- Avoid premature optimization; optimize only after need is proven in use.
- Avoid hidden ordering: have methods call prerequisite submethods, merge methods, use the builder pattern, or encode prerequisites in types; at minimum, name methods to reveal the requirement.
- Prefer specific, longer, descriptive names over short ones.
- Make argument constraints visible: precise types, JSON Schema for flexible payloads, documentation as a last resort.
- Group code by business domain, not just technical layer; aim for high cohesion and low coupling to shrink change blast radius.
- Keep APIs small: add only immediately needed methods/fields, strip unused generator boilerplate, and give fields sensible defaults.
- Publish API schemas so client and server code can be tested against them automatically.
- Prefer backward-compatible API changes; never add required fields ("required is forever").
- Evolve incompatible field changes by adding new fields and deprecating old ones (keep field ordinals stable); monitor deprecated-field usage and clean up after upgrades or a deprecation deadline.
- Watch semantics, not just fields — behavior changes can be incompatible too.
- Version customer-facing APIs; defer to your company's versioning scheme, and keep versioned docs in the code repository so PRs update both together.
- Run schema-compatibility checks at commit time and exercise DDL plus integration tests in preproduction before production.
- Back up tables before destructive migrations; don't trust rollbacks to restore deleted data.
- Decouple schema migrations from application deployments.
- Route every schema change through the chosen migration tool, with the schema history in version control and reviewed via pull requests.
- Learn from the DBA/ops/SRE teams who own large-scale data changes.

## Pitfalls & Anti-patterns

- **Guessing future requirements or building abstraction escape hatches** — the two default tactics for unknown futures; both lead to complexity.
- **Premature optimization** — caches, sharded databases, and queues added before shipping; the optimization turns out unneeded, never gets removed, and complexity accrues (and a cache can go inconsistent with its underlying data).
- **Unnecessarily flexible abstractions** (plugin architectures, wrapper interfaces, generic key-value structures) — they box implementations into rigid boundaries you fight later and make code harder to read; wrappers over divergent backends force a uselessly broad union or a uselessly narrow intersection of features.
- **The cool-feature pitfall** — mistaking your own usage for most users' needs, assuming a feature is easy to add, or building it because it's neat.
- **Implicit knowledge in APIs** — hidden ordering requirements that explode at runtime, and hidden argument requirements where signatures accept more than the method allows.
- **Short, vague names** — they increase cognitive load despite looking cleaner; specific, longer names are easier to understand.
- **Exotic, nonstandard code** — hand-rolled versions of standard library functions and unidiomatic patterns surprise developers and create obscurity.
- **God objects, global state, excessive indirection, action at a distance** — symptoms of high obscurity.
- **Organizing growing systems purely by technical layer** — tier-based teams raise coordination costs (every business change slices through all tiers), and shared layers invite mixing business logic across domains.
- **Incompatible API changes** — including required-field additions, wire-type changes, and semantics changes; runtime breakages may not be immediately obvious.
- **Required fields in serialization schemas** — such an evolvability problem they were removed from Protocol Buffers v3; "required is forever."
- **Dogmatic internal API versioning** — versioning matters most for clients you can't change (customers); internally it may be unnecessary overhead.
- **Shared databases** — schemas become an unofficial, deeply entrenched API; you lose autonomy, data protection, semantic clarity, schema isolation, performance isolation, and possibly security boundaries. Acceptable only as a temporary state (monolith breakup, early-stage cost saving) that must eventually be split.
- **Schemaless data as a default** — an implicit read-time schema that degrades into an unintelligible hodgepodge of record types; it makes evolution harder because you don't know what you're breaking.
- **Hiding schemaless data inside schematized data** (JSON blobs in a "data" column, arbitrary string maps) — all the pain of explicit schemas, none of the gain.
- **Manual DDL against production databases** — divergent environments, uncertain state, unknown authorship, unclear performance impact: error-prone changes plus downtime potential is an explosive combination.
- **Coupling schema migrations to application deployment** — schema changes are delicate with serious performance implications and need independent control.
- **Circumventing the chosen migration tool** — tracked state diverges from reality, negating the tool's value.
- **Trusting rollbacks to undo destructive changes** — rolling back a column deletion restores the column, not its data.
- **Assuming your database is a hidden implementation detail** — ETL pipelines, CDC consumers, reports, ML models, and ad hoc queries depend on your schema; dropping a column can halt them all.

## Key Terms

- **Evolvable architecture**: software structured to accommodate changing requirements; achieved by eschewing complexity.
- **Requirements volatility**: changing customer demands; an unavoidable challenge that can destabilize development.
- **Complexity** (Ousterhout): anything related to a system's structure that makes it hard to understand and modify.
- **Dependency**: reliance of code on other code's API or behavior; necessary, but each connection makes change harder.
- **Tight coupling**: modules that depend heavily on one another.
- **Change amplification**: a single change requiring modifications in dependencies as well.
- **Obscurity**: difficulty predicting a change's side effects, code behavior, and where changes belong.
- **God object**: an object that "knows" too much; an obscurity symptom.
- **Action at a distance**: behavior affected from distant parts of the program.
- **Inertia**: software's tendency to stay in use; high-inertia, high-change systems deserve simplification.
- **KISS**: "keep it simple, stupid" — build with simplicity in mind.
- **YAGNI**: "you ain't gonna need it" — don't build things you don't need.
- **MVP (minimum viable product)**: the bare-minimum feature set needed to get user feedback.
- **Premature optimization**: adding performance optimization before it's proven needed.
- **Muntzing**: asking what is absolutely necessary and throwing away the rest.
- **Principle of least astonishment**: don't surprise users or developers; behavior should match first expectations.
- **Implicit knowledge**: nonobvious information needed to use an API that isn't part of the API itself.
- **Ordering requirement**: actions that must occur in a specific sequence.
- **Builder pattern**: construction pattern that can eliminate method-ordering requirements.
- **Cohesion**: related methods, variables, and classes living near each other; high cohesion is desirable.
- **Decoupled code**: self-contained code whose logic changes don't require changes elsewhere.
- **Domain-Driven Design (DDD)**: architectural approach with extensive concepts and practices for mapping business concepts to software.
- **IDL (interface definition language)**: machine-readable API definition (OpenAPI, Protocol Buffers, Thrift) enabling codegen, validation, docs, stubs, and discoverability.
- **Field ordinals**: the numbers Protocol Buffers uses to refer to fields internally; fields can be renamed if the number stays the same.
- **Forward-compatible change**: clients can use a new API version when invoking an older service version.
- **Backward-compatible change**: new service/library versions don't require changes in older client code.
- **API gateway / service mesh**: infrastructure that routes versioned requests to matching service instances.
- **Cruft**: accumulated maintenance baggage, e.g., logic for dealing with deprecated fields.
- **Autonomy**: a developer's or team's ability to make independent changes to the system.
- **Schemaless data**: data with an implicit schema supplied or inferred at read time.
- **DDL (database description language)**: commands that define and alter database schemas.
- **Schema migration**: a tracked change moving a database schema from one version to another.
- **ORM (object-resource mapper)**: data-access mapping layer; many include schema migration managers.
- **Rollback**: undoing a migration's changes; restores structure but not deleted data.
- **DBA (database administrator)**: specialist who typically runs schema migrations.
- **Data warehouse**: a database used for analytic and reporting purposes.
- **ETL (extract, transform, load)**: pipeline extracting data from production databases, transforming it, and loading it into a warehouse.
- **Change data capture (CDC)**: event-based architecture converting inserts, updates, and deletes into messages for downstream consumers.
- **Data product**: a published user-facing schema (possibly just a database view) that decouples internal schemas from downstream consumers.
