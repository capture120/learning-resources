# Chapter 8 Examples: Delivering Software

### The vocabulary trap: what "released" means on different teams
The chapter opens by noting that delivery phases have no industry-standard definitions, and words like "release" and "deploy" can refer to completely different parts of the pipeline. One team might call the whole process from packaging to rollout "releasing." Another might call packaging an artifact a "release" while calling making it downloadable "publishing." A third might refuse to say a feature is "released" until it's turned on in production, calling everything before that "deployment."
**Lesson:** Pin down your team's delivery vocabulary before assuming anything; identical terms describe different pipeline stages across organizations.

### The four-phase delivery pipeline (figure)
A figure shows delivery as four chevron arrows in sequence: Build, Release, Deploy, Rollout. Software is first built into immutable, versioned packages; packages are released by publishing them to a centralized repository with updated release notes and changelogs; released artifacts are deployed to preproduction and production environments, where they are installed but not yet accessible to users; rollout then shifts users onto the new software, completing delivery. After rollout, feedback, bugs, and new requirements feed the next cycle.
**Lesson:** Deployment and delivery are distinct — installed software counts for nothing until users are actually running on it.

### Trunk-based branching with a cherry-picked bug fix (figure)
A branch diagram illustrates trunk-based development: a short-lived feature-1 branch is cut from trunk and merged back, a bug-1 branch is created to fix a bug, and a release-1.0 branch has been cut. The developers cherry-pick the bug fix into the 1.0 release so the released line gets the fix without taking other in-flight changes.
**Lesson:** In trunk-based development branches stay small and short-lived, and release branches selectively receive fixes via cherry-picking.

### Gitflow's anatomy — and its creator's retraction (figure)
Vincent Driesen described Gitflow in 2010, and a figure shows it in action: long-lived feature-1 and feature-2 branches exchange commits with a develop branch; a release branch carries two releases, both pulled into trunk; and a hotfix branch fixes a bug discovered on trunk, with the fix merged into both trunk and develop so feature branches can pull it in. Trunk stays production-ready because it only ever contains stabilized releases. Driesen has since amended his original blog post to discourage Gitflow for software that can be continuously integrated and delivered.
**Lesson:** Gitflow suits multi-version, hard-to-stabilize software, but even its inventor says to prefer trunk-based development when CI/CD is possible.

### One MySQL version, three architecture packages
The chapter lists real Debian package names — mysql-server-8.0_8.0.21-1_amd64.deb, mysql-server-8.0_8.0.21-1_arm64.deb, and mysql-server-8.0_8.0.21-1_i386.deb — all built from the same MySQL version but each compiled for a different CPU architecture: AMD, ARM, and Intel 386.
**Lesson:** A single build commonly fans out into multiple packages, one per target platform, OS, or runtime.

### The Python packaging onion (sidebar)
A sidebar uses Python's long, convoluted packaging history as a case study, drawing on the Python Packaging Authority's "An Overview of Packaging for Python" and two onion-layer diagrams by Mahmoud Hashemi. For libraries the layers are: a bare .py module at the core; sdist, a group of .py modules compressed into .tar.gz (no compiled code); and wheel, which adds compiled native libraries written in C, C++, Fortran, R, or other languages. For applications the onion deepens: PEX bundles Python code plus all library dependencies; Anaconda manages an ecosystem of all installed libraries, not just your app's; freezers bundle the Python runtime itself; then images (system libraries included), containers (sandboxed images), and virtual machines (kernel included) package operating systems and disk images; and at the outermost layer even hardware is a packaging method — plug-and-play embedded systems shipped with application, system libraries, and OS preinstalled. Outer layers are language-agnostic, and many languages have similar patterns.
**Lesson:** Packaging is a stack of nested layers from source file to shipped hardware; understanding your packaging system's assumptions prevents deployment issues.

### Go distributes dependencies through Git
Go skips a centralized package repository: dependencies are expressed through Git URIs, usually GitHub repositories, so version control doubles as the release repository. The chapter allows that this can work but warns that VCSs aren't built for the purpose — they lack release-oriented search and deployment features, aren't designed for large deployments, and can be overwhelmed when the same machines serve developer checkouts, tooling requests, and deployment fan-out, since developers make frequent small commits with few checkouts while deployments check out code from many machines at once.
**Lesson:** A VCS can technically distribute software, but development and deployment load profiles differ so much that purpose-built release repositories are the safer choice.

### The Apache Software Foundation release process (sidebar)
A sidebar presents the ASF's release guidelines as a thorough real-world example. A release manager is nominated to run each project release. Releases include source and often binary packages; release managers sign artifacts with a cryptographic key so users can verify packages came from Apache, checksums detect corruption, LICENSE and NOTICE files declare licenses and copyrights, and all source files carry license headers. The release manager "cuts" a release candidate, and project management committee (PMC) members vote to accept or reject it — they're expected to validate the final artifacts before voting by checking checksums, signatures, and acceptance tests. Accepted artifacts are posted to downloads.apache.org, after which the release manager announces on project mailing lists and updates the website with release notes, changelogs, new documentation, and a blog post. Apache Spark's release page is cited as a detailed playbook.
**Lesson:** Mature release processes combine verifiable signed artifacts, human validation and sign-off, and deliberate user communication.

### Deployment by wiki: LinkedIn's manual release nights (sidebar)
LinkedIn used to release its web services manually. Developers and site reliability engineers attended prerelease meetings to declare which services and configuration changes were shipping, all recorded on a large wiki page. Because developers weren't properly managing compatibility, release managers had to break services into ordered deployment phases — some services had to roll out before others, some even called each other in circular dependencies, and one deployment had more than 20 phases. On deployment night everyone logged in to an IRC channel while SREs painstakingly copied artifacts to production machines, restarted services, and ran database migration scripts step by step into the early morning. Deployments were slow and costly because they had to be done manually, and automation beyond simple scripts was difficult; a single failed service blocked all downstream phases, each phase needed manual verification before the next could proceed, and deploys were aggravating, stressful, and tedious. LinkedIn eventually banned deployment ordering: services had to support independent deployment or they weren't allowed to ship. The ban forced a lot of rework — services, tests, tooling, and deployment processes all changed — but deployments became completely automated, developers delivered at their own cadence (multiple times per day if desired), SREs stopped babysitting deployments, and everyone got more sleep.
**Lesson:** Deployment ordering makes releases slow, fragile, and miserable; mandating independently deployable, compatible services costs effort once and pays off permanently.

### The symlink flip: atomic installs by never overwriting
The chapter's recipe for atomic deployment: install the new version into a different location than the old one — overwrite nothing — then flip a single shortcut or symbolic link to activate it. The motivation is that installation steps fail for mundane reasons: machines run out of disk, restart at the wrong time, or have unexpected file permissions, and a partial install that corrupts the previous good one (or leaves debris that breaks scripts assuming empty directories) poisons future deployments. Side-by-side installs make rollback a matter of pointing the link back at the old version, and sometimes let different versions run simultaneously on one machine.
**Lesson:** Make deployments all-or-nothing by installing alongside rather than over the previous version, so failures never destroy a working install and rollback is trivial.

### Feature flag ramp: test accounts, one customer, then percentages
The chapter sketches the common rollout progression with feature flags: start by enabling the feature only for company-owned test accounts, then ramp to a single real customer, then proceed with an incremental percentage-based release to ever-larger swaths of users. Flags themselves range from on/off Booleans to allow lists, percentage ramps, and small functions that compute the flag from request parameters at request time.
**Lesson:** Ramp exposure gradually from internal accounts outward so problems surface before most users ever see the new code.

### The stale feature flag hazard
The chapter warns about code littered with old feature flags: it becomes difficult to reason about and can even cause bugs — specifically, turning off a feature that has been on for a long time can create havoc, and state written while a flag was off still exists when it's flipped back on. The prescribed discipline: create tickets to remove old flags, and clean them up incrementally and opportunistically, like refactoring.
**Lesson:** Feature flags are temporary scaffolding; left in place they become a source of confusion and latent bugs.

### Circuit breakers in the wild: email, bank transfers, and read-only databases
Three illustrations of circuit breakers — flags flipped by operational events rather than humans: when a latency threshold is exceeded, certain features are automatically disabled or rate limited (circuits can also break on anomalous logs, like exceptions or a jump in verbosity); applications that take irreversible actions, such as sending an email or transferring money out of a bank account, trip a breaker when it's unclear whether to proceed; and many databases and filesystems automatically flip themselves to read-only mode when they detect disk corruption.
**Lesson:** Automated, binary, permanent kill switches stop degraded systems from causing irreversible damage faster than any human could react.

### Canary deployment at 1 percent (figure)
A figure shows a load balancer routing 99 percent of inbound traffic to a fleet running Service 1.0 and 1 percent to a single instance running Service 1.1. Named for the canary in a coal mine that warned miners of dangerous gases, the canary instance is an early warning system for the new version: if it malfunctions, only a small portion of users is affected, and they can be quickly routed back to the old version.
**Lesson:** Expose a new version to a tiny traffic slice first so failures are small, detectable, and instantly reversible.

### Blue-green deployment flip (figure)
A figure shows two complete environments behind a load balancer: a passive ("blue") cluster running version 1.0 and an active ("green") cluster running 1.1 receiving 100 percent of traffic. The new version is deployed to the passive environment; when ready, traffic flips atomically to it, and the previous version becomes the passive fallback — problems mean flipping back. The environments are kept as identical as possible, each must handle full traffic, and in the cloud the passive one is usually destroyed once the release is stable. The pattern fits when traffic can't easily be subset, and the ability to stand up a parallel environment fast is invaluable in disasters requiring migration off a misbehaving system.
**Lesson:** Keeping a complete previous environment on standby turns rollback into an atomic traffic flip.

### Dark reads and dark writes (figure)
A figure contrasts the two shadowing modes. In dark reads, the load balancer duplicates read requests to a dark service whose responses are discarded; the dark service may share the production database since nothing is modified. In dark writes, write traffic is also duplicated, so the dark service uses a completely independent datastore. In both, responses from live and dark systems are compared and differences recorded, while only production responses reach users. Because every operation happens twice, dark traffic must be excluded from user analytics and side effects like double billing must be prevented — requests are marked via headers, and tools like the Istio service mesh and the Gloo API gateway support this natively.
**Lesson:** Shadowing real traffic lets you observe new code in production with zero user impact, provided you guard against duplicated side effects.

### Diffy: filtering nondeterministic noise from dark traffic
The open source tool Diffy sends dark traffic to three backend instances: two running the production code and one running the new release candidate. It compares new-versus-old responses to identify all differences, and compares the two identical old instances to identify nondeterministic noise. Subtracting the noise lets Diffy automatically isolate expected differences and remove false positives.
**Lesson:** Comparing two copies of the old version gives a baseline of natural nondeterminism, so only real behavioral changes get flagged.

### "We Want It Darker": dark writes rescue a decaying Twitter service (sidebar)
Through a series of org changes during rapid growth, a key service at Twitter fell into disrepair: heavy technical debt, a constant stream of feature requests, and every production change risky because the service was tricky to test and corner cases kept surfacing. The lone engineer maintaining it was overwhelmed — time went to debugging production problems, frequent bugs slowed new changes, the backlog grew, pressure mounted, and new features kept making the codebase more complex. After another reorganization, the engineer and service landed on author Dmitriy's team, whose tech lead declared the situation untenable: feature work had to stop until the debt was addressed. The team focused on production stability using dark writes, building a variant of the Diffy approach that compared objects in a stream rather than HTTP responses — within two weeks. The service now had a safety net: new versions could "bake" as long as desired while the team analyzed unexpected differences in produced data; they could dark launch a change, let real user traffic reveal edge cases, capture them, add tests, fix, and retry. The test suite grew, the development cycle accelerated, and confidence in releases rose. The maintaining engineer said it felt like a mountain had been lifted off their shoulders, and refactoring, performance work, and even new features started moving quickly — in the authors' words, dark writes were what allowed the sun to finally rise.
**Lesson:** When a system is too fragile to change safely, shadowing real traffic builds the safety net that makes refactoring, testing, and renewed velocity possible.

### Recommended further reading
The chapter closes with named references: *Git for Teams* by Emma Jane Hogbin Westby (O'Reilly, 2015) for branching strategies, foundational even beyond Git; *Continuous Delivery* by Jez Humble and David Farley (Addison-Wesley, 2010) as the deep dive on the chapter's topics for anyone spending serious time on release engineering; Google's *Site Reliability Engineering* (O'Reilly, 2016), whose own Chapter 8 covers release engineering, as a shorter read; *Release It!* by Michael T. Nygard (Pragmatic Bookshelf, 2018) for operations and operational design patterns, highly recommended for web service developers; and Amazon's free Builder's Library for posts on continuous delivery, automated deployment, and rollbacks.
**Lesson:** Delivery is a deep specialty with a well-established canon to consult when release engineering becomes a bigger part of your job.
