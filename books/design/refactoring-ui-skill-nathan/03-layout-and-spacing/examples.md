# Layout and Spacing — Examples from the Book

All figures paraphrased. Bad/weak versions are marked X in the book; improved versions are marked with a check.

## Start with too much white space

**Two-factor authentication setup card.** A modal-style card ("Set up Two-Factor Authentication", step 1 of 3, with a country selector, phone number input, and Next Step button). Weak version: header, section title, helper text, labels, inputs, and button are packed tightly with minimal padding, so the card reads as one undifferentiated block. Improved version: same content with substantially more padding around the card edges and larger gaps between the header block, the "Setup your phone" section, and the input row. Nothing else changed — only space — and the card immediately looks cleaner and more professional.

**Customer reviews widget (adding space reactively).** A card titled "50 customer reviews" with five horizontal star-rating bars (5 star 56%, 4 star 20%, etc.), a "Review this product" subheading, and a "Write a review" button. The cramped version (X) has the bars nearly touching. A second version (marked "?") adds just enough margin that it no longer looks bad. The lesson: adding space until things stop looking cramped only reaches the minimum acceptable amount, not the best amount.

**Customer reviews widget (subtracting from excess).** Same widget demonstrating the recommended workflow. First version: deliberately exaggerated spacing — very large gaps between every rating bar and around the title and button (this is the starting point, marked X here because it's the "way too much" stage, not the final design). Final version (check): spacing dialed back from that maximum until it feels right. The end result has noticeably more space than the "just stopped looking bad" version, and what felt excessive on the isolated widget feels right in a full UI.

**Hockey game summary dashboard (when density is right).** A sports dashboard for Canada vs. United States: team stats (shots on goal, faceoff %, power play, penalty minutes, hits, blocks), a scoring summary with player avatar, and a dense table of forwards with goals/assists/points columns. Information is tightly packed so everything fits on one screen at once. This is presented as legitimate: when a user needs lots of data visible simultaneously, compact layout is worth the busier feel — as long as it's a deliberate choice.

## Establish a spacing and sizing system

**Hotel listing card with arbitrary values (weak).** A booking card for a "Premier Suite" at $450/night with a photo, a "View Rates" button, a favorite button, and a "Highlights" bullet list. Annotations expose the measured spacing: 26px, 24px, 26px, 12px, 15px, 21px, 25px, 13px, 22px — near-duplicate values like 24/25/26 and 12/13/15 scattered around. These came from eyeballing pixel by pixel; the result is subtly inconsistent and was slow to produce.

**Download button at three icon/spacing sizes (small values are sensitive).** The same blue "Download" button shown at 16px (a 20% decrease), 20px (actual size), and 24px (a 20% increase). Each step is clearly visible. This demonstrates that at the small end of the scale a few pixels change an element's character — 12px to 16px is a 33% jump.

**Delivery feature card at 500px vs 520px (large values are insensitive).** A "Citywide Delivery" card with icon, description, and "Learn more" link shown at 500px wide and at 520px wide (a 4% increase). The difference is essentially invisible. Together with the button example, this motivates a scale where adjacent values are never closer than ~25%: small steps cluster, large steps spread out.

**The 16px-based scale.** A bar chart showing the recommended scale: 4, 8, 12, 16, 24, 32, 48, 64, 96, 128, 192, 256, 384, 512, 640, 768px, each labeled as a multiple of 16 (×0.25 up to ×48). The gap between adjacent bars grows as values get larger, keeping every step meaningful.

**Hotel listing card on the system (improved).** The same Premier Suite card rebuilt using only scale values. Annotations now read 24px, 24px, 24px, 12px, 12px, 24px, 24px, 12px, 24px — two values doing the work that nine arbitrary ones did before. The card gains a subtle consistency, and every decision was a quick pick from the scale instead of pixel-nudging.

## You don't have to fill the whole screen

**UrbanFair shopping cart (full-width vs constrained).** An e-commerce cart page: item row (Eleanor Chair, $429), discount code input with Apply button, subtotal/taxes, and total. Weak version: the layout stretches across the entire browser window, so product names sit far left while their prices sit far right, and the discount input becomes enormously wide — the eye must travel to connect related data; the store header pins the URBANFAIR logo to the far left edge and the Shop/search/cart controls to the far right. Improved version: the entire page — the store header with logo and Shop/search/cart controls included, not just the cart table — is constrained to the same narrow centered column. Related information sits close together and the page is easier to scan; the empty space at the sides costs nothing. (Contrast with the login page below, where the nav deliberately stays full-width while only the card is narrow — the book marks both treatments as good.)

**Login page under a full-width nav.** A page with a full-width navigation bar (Features, Pricing, Blog, Documentation, Sign up) and below it a small centered "Welcome Back!" login card with username, password, remember-me, and a log in button. Shown as a positive example: the nav being full-width does not force the login form to be full-width. Each section gets only the width it needs.

**Podcast app, mobile first (shrink the canvas).** A podcast player ("Weekend Hackers" show page with a subscribed badge, a play card for the latest episode, and a past-episodes list) designed first on a phone-sized (~400px) canvas. The real constraint makes the small design easier to get right. The mobile top bar collapses navigation behind a hamburger icon (plus a search icon) — the one real compromise the small screen forced. The follow-up figure shows the same design brought to a desktop browser: the hamburger is replaced by visible Browse and Library nav links and the hero banner widens, but the show header, play card, and episode list carry over nearly unchanged. Restoring the collapsed navigation is essentially the only change needed — the concrete instance of "adjust anything that felt like a compromise on smaller screens." Lesson: design mobile first, then enlarge and fix only what felt like a compromise — less changes than you'd expect.

**Playback account settings form (thinking in columns).** A settings page ("Account Settings" with Basics and Profile sections: email, password, language, country, names, picture, username). Weak version: a single narrow column where each section heading and its helper text sit stacked above the fields — correct form width, but it floats awkwardly in the wide page. Improved version: a two-column layout where each section's heading and supporting text move into a left-hand column and the inputs occupy the right. The page now uses the available width and feels balanced, while the form fields keep their optimal narrow width.

## Grids are overrated

**12-column grid anatomy.** A wireframe overlaid with 12 pink columns showing what "on the grid" means: every element's width is a multiple of 8.33% (including gutters) — e.g., 3 columns = 25%, 6 columns = 50%, 3 columns = 25%.

**Percentage sidebar breaks at both extremes.** A classic app layout: sidebar at 3 columns (25%), content at 9 columns (75%). At default width it looks fine. Widened, the sidebar balloons, wasting space the content area could use. Narrowed, the sidebar shrinks below the minimum width its labels need, causing awkward wrapping and truncation. The percentages preserve a ratio nobody actually wants preserved.

**Invoice dashboard with a fixed sidebar (improved).** A dashboard app (Dashboard/Invoices/Expenses/Time Tracking nav, invoice cards with amounts and Pending/Overdue/Paid badges) shown at a wide width and a narrow width. The dark sidebar keeps the exact same fixed width in both; the main content area flexes, showing four invoice cards when wide and two when narrow, laid out by its own internal grid. The sidebar is sized for its content, and resizing never degrades it.

**Comment card with fixed avatar.** A social post card (Kimberly Kennedy, Sr. Front-End Developer, with avatar, timestamp, and message) shown at two card widths. The avatar keeps a fixed pixel size in both; only the text reflows. Demonstrates the rule inside components: use percentages only when you actually want an element to scale.

**Login card sized by grid columns (the absurdity).** A "Welcome Back!" login card sized at 6 of 12 columns (50%) with a 3-column offset on each side on large screens. On medium screens it felt too narrow, so it was bumped to 8 columns there (two empty columns per side). Because columns are fluid percentages, there is a band of viewport widths where the card renders wider on a medium screen than on a larger screen — the layout literally inverts the intended relationship. The fix shown: give the card a max-width (e.g., its optimal ~500px) at every screen size; in the two larger of three browser widths the card renders identically; only in the narrowest browser, where the viewport drops below the max-width, does the card shrink to fit (visibly narrower, with slim side margins).

## Relative sizing doesn't scale

**Article headline in em units.** A marketing article with 18px body copy and a 45px headline ("Team communication optimized for deep work"), with the headline encoded as font-size: 2.5em. On desktop this looks right. On mobile (X), body copy drops to 14px to keep line length readable, and 2.5em now renders the headline at 35px — comically large, wrapping over four lines and dominating the small screen. Improved mobile version (check): headline set directly to 24px (the book suggests 20–24px), which is only 1.5–1.7× the body. The desktop ratio (2.5×) and mobile ratio (~1.6×) differ so much that no fixed relationship was ever real — so define sizes per context.

**Buttons with proportional vs tuned padding.** Four sizes of a blue "Button" component. Proportional version (X): padding scales exactly with font size — 20px font with 15×20 padding, 16px with 12×16, 14px with 10.5×14, 12px with 9×12 (i.e., padding pinned at 0.75× the font vertically and 1× horizontally, the result of defining padding in font-relative units so one font-size change resizes the whole button). It works mechanically but the set looks like the same button at different zoom levels. Tuned version (check): padding grows faster than the font at large sizes and shrinks faster at small sizes — 20px font with 15×30, 16px with 12×16, 14px with 8×10, 12px with 6×8. Figure detail: the 16px entry is identical in both sets; it acts as the anchor, with tuning diverging above and below it. A second figure detail: at the largest size, all the extra generosity is horizontal — 15×30 versus the proportional 15×20 keeps vertical padding identical, so the big button gets wider and more substantial without getting taller. At the small sizes both axes shrink below proportional (8×10 vs 10.5×14 at 14px; 6×8 vs 9×12 at 12px). To make a large button feel large, the knob to turn is horizontal padding. The large button now feels genuinely substantial and the small ones feel genuinely compact.

## Avoid ambiguous spacing

**Restaurant list with explicit separators (baseline).** A map app's ranked restaurant list (260 West, Lakeside Restaurant, Everly's Kitchen, each with stars, review counts, price level, cuisine, address, hours, and a photo). Each result sits in its own bordered card, so grouping is unambiguous without any spacing tricks. This frames the problem: when separators are absent, spacing alone must do this job.

**Billing address form (label/input ambiguity).** A checkout step ("Billing Address") with stacked fields: Full name, Street address, City, Province/Territory. Weak version: 20px below each input and 20px below each label — every gap identical, so each label floats equidistant between two inputs and could belong to either. At best the user parses harder; at worst they enter data into the wrong field. Improved version: 20px between field groups but only 10px between a label and its input. Each label now visibly belongs to the field below it. (A prose-versus-figure nuance: the text frames the fix as increasing the space between form groups, while the annotations keep the 20px group gap and halve the within-group gap to 10px — either lever produces the same required contrast.)

**Article section heading.** Body text followed by a bold section heading ("Monday morning has arrived.") followed by more body text. Weak version: 24px above and 24px below the heading — it floats between sections, attached to neither. Improved version: 36px above and 12px below — the heading clearly introduces the text beneath it.

**Bulleted list with wrapping items.** A "Join our growing community" checklist where items wrap to two lines. Weak version: 24px between bullets while the line-height within a wrapped bullet is also 24px — a wrapped item's second line is as far from its first line as it is from the next bullet, so items blur together. Improved version: line spacing stays 24px but the gap between bullets increases to 36px, making each item read as a unit.

**Social card action row (horizontal ambiguity).** A post by Amber Matthews with an action bar: thumbs-up icon, count "45", comment icon, count "17", share icon, "Share". Weak version: 16px on both sides of each count — the number "45" sits equally close to the like icon and the comment icon, so it's unclear which it counts. Improved version: 6px between an icon and its own count, 36px between action groups. Each count snaps to its icon, and the groups separate cleanly. The closing rule: whenever spacing implies grouping, the space around a group must exceed the space within it.
