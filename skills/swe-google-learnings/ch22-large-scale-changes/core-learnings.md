# Chapter 22: Large-Scale Changes

## Chapter Thesis

As a codebase and the number of engineers working in it grow, the largest change that can be committed atomically counterintuitively *shrinks*: presubmit checks take too long, merge conflicts multiply, and version-control operations hit technical limits. Google therefore abandoned sweeping atomic commits and instead built a discipline of **large-scale changes (LSCs)**: automatically generated sets of logically related edits that are sharded into many small, independently tested, reviewed, and committed pieces. The chapter argues that a mature LSC capability — combining tooling (code indexing, change generation, the Rosie sharding platform, the TAP testing train) with social structures (a lightweight approval committee, global approvers, cultural trust in infrastructure teams) — is what keeps a large codebase malleable, lets infrastructure teams migrate everyone off old systems, and makes formerly "permanent" technical decisions reversible.

## Core Principles and Ideas

### What an LSC is

- An **LSC (large-scale change)** is any set of logically related changes that cannot practically be submitted as a single atomic unit — because the tooling cannot commit that many files at once, because a change that large would always hit merge conflicts, or because the code lives across distributed/federated repositories where cross-repo atomic commits are impossible.
- LSCs at Google are almost always generated by automated tooling, not typed by hand.
- Common categories of LSCs:
  - Cleaning up common antipatterns found by codebase-wide analysis tooling.
  - Replacing uses of deprecated library features.
  - Enabling low-level infrastructure improvements such as compiler upgrades.
  - Moving users from an old system to a newer one.
- Most LSCs have near-zero functional impact: they are behavior-preserving refactorings for clarity, optimization, or future compatibility. But LSCs are not limited to that class.
- Scale at Google: infrastructure teams routinely change hundreds of thousands of references; the largest efforts have touched millions. Roughly 10–20% of changes in a typical Google project come from LSCs made by people whose full-time job is unrelated to that project.

### Who runs LSCs, and why centralization wins

- Centralized **infrastructure teams** — the owners of the system being migrated — run LSCs rather than mandating that every consuming team migrate itself. Three reasons:
  1. **Domain knowledge.** The infrastructure team already understands the system and its failure modes; expecting hundreds of consumer teams to each relearn that expertise is globally inefficient. Errors fall into a small set of categories, so a central team can keep a playbook for fast recovery.
  2. **No unfunded mandates.** An "unfunded mandate" is a requirement imposed on teams with no compensating resources. The benefits of a new system are diffuse across the organization, so individual teams rarely migrate on their own initiative. Centralizing the migration internalizes those costs and makes them cheaper via economies of scale.
  3. **Aligned incentives.** Organic (voluntary, decentralized) migrations rarely fully succeed, partly because engineers copy existing code as examples. A team with a vested interest in *removing* the old system ensures the migration actually finishes.

### Barriers to atomic changes

Four forces make single giant commits infeasible:

1. **Technical limitations.** Most version control systems have operations that scale linearly with change size; committing thousands of files at once may exceed memory or processing capacity, and in centralized VCSs large commits can block other users.
2. **Merge conflicts.** The probability of a merge conflict grows with the number of files in a change, compounded by the number of engineers active in the repository. At a large global company, someone is always committing; there is no quiet weekend window.
3. **Haunted graveyards.** A "haunted graveyard" (a term from Google's Site Reliability Engineers) is a system so ancient, obtuse, or complex that no one dares touch it — often business-critical code frozen in time by fear and bureaucracy. Haunted graveyards block migrations, decommissions, and compiler/library upgrades. The antidote is thorough **testing**: well-tested software can be changed with confidence regardless of its age or complexity.
4. **Heterogeneity.** LSCs work only when computers do the bulk of the effort, and automation needs consistent environments. Many different VCSs, CI systems, project-specific tools, or formatting rules make sweeping automated change difficult. Consistency helps both humans and "the robots."

Additional cross-cutting barriers:

- **Testing at scale.** The farther a test sits from the changed files in the dependency graph, the less likely a failure is actually caused by the change. Small independent changes are easier to validate and debug (finding a root cause in 25 files is easy; in 10,000 files it is a needle in a haystack). Google consciously trades extra compute (rerunning tests for many small shards) for saved engineer time, because engineer time is far more expensive.
- **Code review at scale.** Reviewing giant commits is tedious and error-prone; sharding an LSC makes human verification tractable.

### The TAP train (testing many LSCs together)

**TAP (Test Automation Platform)** is Google's continuous-integration system. Because a large LSC could trigger a rerun of every test at Google, TAP batches LSCs into a "train" that departs fresh every three hours. The train exploits two facts: LSCs are usually narrow, semantics-preserving refactorings, and individual machine-generated changes are highly scrutinized and usually correct. The five steps:

1. For each change on the train, run a sample of 1,000 randomly selected tests.
2. Gather all changes that passed their 1,000 tests into one combined "uber-change": the train.
3. Run the union of all tests directly affected by the group. For a large or low-level LSC this can mean every test in the repository and can take more than six hours.
4. For each non-flaky failing test, rerun it individually against each change on the train to find the culprit.
5. TAP produces a per-change report of passing and failing targets, usable as evidence the LSC is safe to submit.

### LSC infrastructure

- **Policies and culture.** Google's monorepo lets any engineer edit any file, and cheap change generation lets one engineer impose review burden on the whole company. So Google added a lightweight approval process overseen by experienced engineers plus invited domain experts. The goal is not to prohibit LSCs but to improve them (and occasionally to say a cleanup is not worth doing). Culturally, product teams learned to trust infrastructure teams' domain expertise; local owners may ask questions but **do not hold a veto** over a broader LSC. A good FAQ and a track record of improvements built widespread endorsement.
- **Codebase insight.** Large-scale textual *and semantic* analysis is essential. **Kythe** is Google's semantic indexing tool, providing a complete map of links in the codebase ("who calls this function?", "which classes derive from this one?") with programmatic access for refactoring tools. Compiler-based tools such as **ClangMR**, **JavacFlume**, and **Refaster** run abstract-syntax-tree–based transformations in a highly parallel way. Smaller changes can use sed, perl, regexes, or shell scripts.
- **Sublinear human effort.** Whatever the tooling, human effort must scale *sublinearly* with codebase size: generating all required changes should take roughly the same human time regardless of repository size, and the tooling must be comprehensive so authors know they covered every case.
- **Change management: Rosie.** **Rosie** is Google's LSC platform. It shards a master change into smaller pieces along project boundaries and ownership rules, then drives each shard through an independent test–mail(review)–submit pipeline. Rosie caps outstanding shards, runs at lower priority, and coordinates load with shared testing infrastructure.
- **Testing infrastructure.** LSC shards skip standard project-based presubmits; instead each shard runs the transitive closure of every test it might affect. A robust testing culture is what lets tooling trust machine-generated changes.
- **Language support.** Language features like **type aliasing** and **forwarding functions** allow old and new systems to coexist during a non-atomic migration; languages lacking them are hard to migrate incrementally. Statically typed languages (with compiler-based tools and strong static analysis) are far easier to change automatically than dynamically typed ones (Python, Ruby, JavaScript), which makes "developer-productivity-focused" languages harder to maintain long term. **Automatic formatters** (clang-format, google-java-format) are crucial: every LSC tool runs the formatter as a separate pass so machine-generated changes read like human-written code. Without automated formatting, LSCs would never have become accepted at Google.

### The LSC process (four phases)

1. **Authorization.** The author writes a brief document: the reason for the change, estimated impact (how many shards), an FAQ, and a proposed change description, plus "domain review" from the owners of the API being refactored. A committee of about a dozen experienced engineers gives feedback (commonly: route all reviews to a single **global approver** rather than local owners). Approval is historically liberal and often covers a broad set of related changes; the committee also serves as the escalation body when local owners object.
2. **Change creation.** The author generates the code edits, as automatically as possible so the parent change can be regenerated as users backslide into old patterns or merge conflicts appear. Rarely, generation itself is sharded across humans (see Operation RoseHub). Output must look human-written, hence formatters and style guides.
3. **Shard management (sharding and submitting).** Rosie shards the global change and runs each shard through test → mail → review → submit:
   - **Testing:** each shard runs its transitive test closure; shards affecting huge test sets are batched (run the union first, then per-shard only the intersection with what failed). Recently flaky tests are ignored by the submit tooling because a scrutinized machine-generated change is now considered more trustworthy than a flaky test.
   - **Mailing:** Rosie's owners-detection service reads OWNERS files, weights reviewers by fitness, and adds reviewers if someone is unresponsive. Nonstandard per-project checks (e.g., change-description format rules) are selectively disabled; preexisting presubmit failures are aggressively ignored — keeping the codebase free of them is the local owners' side of the social contract with infrastructure teams.
   - **Reviewing:** changes needing local *context* go to local owners; everything else goes to a global approver who uses pattern-based tooling to auto-approve expected changes and manually examines only anomalies (merge conflicts, tooling malfunctions).
   - **Submitting:** each shard must still pass project precommit checks before commit. With Rosie, Google creates, tests, reviews, and submits thousands of changes per day.
4. **Cleanup.** Definitions of "done" vary — from fully deleting the old system to migrating only high-value references. In almost all cases you need a mechanism that prevents *reintroduction* of the removed symbol or system. Google uses the **Tricorder** static-analysis framework to flag new uses of deprecated objects at review time, which effectively prevents backsliding.

### Cattle versus pets

Ordinary handcrafted changes are "pets": an engineer nurtures one change for days or weeks and takes rejection personally. LSC shards must be treated as "cattle": nameless, faceless commits that can be rolled back or rejected at any time at little cost, because automation can regenerate them cheaply. Losing a few cattle is fine unless the whole herd is affected.

## Actionable Guidance

- Invest early and often in LSC tooling; the same tools that change thousands of files also scale down well to tens of files, and they enable cheap opportunistic fixes ("filling potholes") that would otherwise never happen.
- Rule of thumb: if a change requires more than ~500 edits, it is usually cheaper for an engineer to learn and run change-generation tooling than to edit by hand (experienced "code janitors" break even much sooner).
- Centralize migrations in the team that owns the system being replaced; do not issue unfunded mandates to consumer teams.
- Fight haunted graveyards with thorough test coverage rather than freeze-and-fear bureaucracy.
- Reduce heterogeneity: standardize VCS, CI, presubmit behavior, and formatting so automation can operate everywhere; ask teams to waive project-specific checks for LSC shards.
- Prefer many small independently committable shards over one giant commit; accept the compute cost of redundant test runs because engineer debugging time costs more.
- Shard along project boundaries and ownership rules; keep interdependent files (e.g., a header and its implementation) in the same shard.
- Use a single expert global approver with pattern-based review tooling for mechanical changes instead of hundreds of local reviews.
- Hold local owners responsible for keeping their projects free of preexisting presubmit failures.
- Run an automatic language formatter as a separate pass over all generated changes.
- Design *new* systems with an automated migration path from the old system in mind, before the migration starts.
- Establish a lightweight oversight committee: liberal approvals, FAQ requirement, escalation path for disputes, and willingness to reject dangerous or extremely low-value changes (e.g., blanket NULL→nullptr conversion, British↔American spelling wars).
- After migrating, install static-analysis checks (like Tricorder) that block new uses of the deprecated thing.
- Track and suppress flaky tests, and push their costs back onto the teams that own them, because flakiness throttles LSC throughput.

## The Chapter's TL;DRs (verbatim)

- An LSC process makes it possible to rethink the immutability of certain technical decisions.
- Traditional models of refactoring break at large scales.
- Making LSCs means making a habit of making LSCs.
