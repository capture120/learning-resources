# Chapter 22: Large-Scale Changes — Examples and Case Studies

All examples come from "Software Engineering at Google," Chapter 22, written by Hyrum Wright. An LSC (large-scale change) is a set of logically related code changes too big to submit as one atomic commit, so it is generated by tooling and landed as many small independent pieces.

## Case Study: Filling Potholes (stl_util.h vs. map-util.h)

**Setup.** Early in Google's history, engineers built the Google Template Library, a set of C++ header files supplementing the C++ Standard Template Library. Through historical accident, one header was named `stl_util.h` (underscore separator) and another `map-util.h` (hyphen separator). Engineers had to remember which file used which separator and often discovered a mistake only after a long compile cycle, so the inconsistency cost real productivity, not just aesthetic annoyance.

**What happened.** Fixing a one-character naming inconsistency across a codebase of Google's size sounds pointless. But because Google's LSC tooling and process were mature, the library authors fixed every reference themselves in a couple of weeks of background-task effort, without bothering the end users of those files. Google measured a quantitative drop in build failures caused by the naming confusion.

**Lesson.** Simply *having* LSC capability opens up small opportunistic fixes ("filling potholes") that would never justify a manual campaign. Infrastructure work is both building new roads and repairing old ones, and cheap repair capacity changes which fixes are worth doing. It also means engineering decisions are no longer immutable, so teams can decide things knowing they can be revised later.

## Case Study: Testing LSCs and the TAP Train (sidebar by Adam Bender)

**Setup.** At Google, 10–20% of the changes in a typical project come from LSCs, meaning substantial code is changed by people whose full-time job has nothing to do with that project. Even a one-line function-signature change becomes complicated when made in a thousand places across hundreds of products: reviews must be coordinated across dozens of teams, and a good-sized LSC could trigger a rerun of every single test at Google. While the LSC winds through the process, the author's local state drifts permanently out of sync with the head of the repository, and downstream clients keep "backsliding" into the old pattern, so authors must plan time to catch them.

**What happened.** Google built the TAP (Test Automation Platform) train to test many LSCs together instead of one at a time. It rests on two observations: LSCs are usually narrow, semantics-preserving refactorings, and each machine-generated change is highly scrutinized, so most changes are correct and rarely interact with one another. Every three hours a fresh train departs: (1) each candidate change runs a random sample of 1,000 tests; (2) all changes that pass are merged into one "uber-change," the train; (3) the union of all tests affected by the group runs, which for low-level LSCs can mean every test at Google and can take over six hours; (4) each non-flaky failure is rerun against each individual change to identify the culprit; (5) TAP issues a per-change safety report used as submission evidence.

**Lesson.** Without strong test infrastructure and batched testing, LSC work would be impossible and the codebase "would quickly atrophy under its own weight." Batching amortizes enormous test costs across many changes because most LSC shards are independent and correct.

## Case Study: scoped_ptr to std::unique_ptr

**Setup.** From its early days, Google's C++ code used a homegrown smart pointer called `scoped_ptr` — a type that automatically destroys a heap-allocated object when the pointer goes out of scope, preventing memory leaks. It was the best available under the old C++98 standard. C++11 introduced `std::unique_ptr`, which did the same job and also caught additional classes of bugs. `std::unique_ptr` was strictly better, but Google had more than 500,000 references to `scoped_ptr` scattered across millions of source files. The migration was the largest LSC ever attempted at Google to that point.

**What happened.** Over several months, several engineers worked in parallel using Google's large-scale migration infrastructure. They both rewrote references from `scoped_ptr` to `std::unique_ptr` and gradually adapted `scoped_ptr`'s behavior to match `std::unique_ptr`. At the peak, they generated, tested, and committed more than 700 independent changes touching more than 15,000 files per day (Google later reached roughly 10 times that throughput). The long tail included nuanced behavioral dependencies (a manifestation of Hyrum's Law — the observation that with enough users, every observable behavior of a system will be depended on by somebody), race conditions against other engineers' concurrent edits, and uses inside generated code that automated tooling could not detect; these were fixed manually as testing surfaced them. Because `scoped_ptr` appeared as a parameter type in widely used APIs, small independent changes were hard; the team considered a call-graph analysis system to change an API and all its callers transitively in one commit but feared those commits would be too large to land atomically. The endgame: make `scoped_ptr` a type alias of `std::unique_ptr`, then textually substitute the old alias for the new type everywhere, then delete the alias.

**Lesson.** Language features like type aliasing enable non-atomic migration: old and new can coexist while users move over gradually. Only mature LSC tooling made it possible for Google's codebase to converge on the standard C++ ecosystem type. Expect a long manual tail even in a heavily automated migration.

## Case Study: Operation RoseHub (the Mad Gadget vulnerability)

**Setup.** In early 2017, a vulnerability in the Apache Commons Java library — nicknamed "Mad Gadget" — allowed remote code execution in any Java application that merely had a vulnerable library version anywhere in its transitive classpath (the full chain of libraries a program depends on, including dependencies of dependencies). A hacker exploited it to encrypt the San Francisco Municipal Transportation Agency's systems and shut down its operations. Because the bug required only the wrong library somewhere in the dependency chain, huge numbers of open source projects on GitHub were vulnerable.

**What happened.** Googlers volunteered to run the LSC process *outside* Google, on the open source world. Using BigQuery (Google's large-scale data analysis service) they identified affected GitHub projects and sent more than 2,600 patches upgrading those projects' Apache Commons versions to a fixed release. Because Google's automated LSC tooling could not manage external repositories, more than 50 humans manually did the sharded work that tools normally do.

**Lesson.** The LSC *process* — analyze the whole corpus, generate targeted fixes, land them as many independent patches — generalizes beyond one company's monorepo. When automation is unavailable, sharding the generation work across many humans still works and is much faster for time-sensitive fixes, just more labor intensive.

## Analogy: No Haunted Graveyards

**Setup.** Google's Site Reliability Engineers (SREs), who run production services, use the mantra "No Haunted Graveyards." A haunted graveyard is a system so ancient, obtuse, or complex that nobody dares touch it — often business-critical, revenue-carrying code written by someone long gone, frozen by layers of bureaucracy because any change might break it in incomprehensible ways.

**What happened / the point.** Haunted graveyards exist in codebases too, and they are poison to LSCs: they block migrations, block decommissioning of systems they depend on, and block compiler and library upgrades. Google's counter is thorough testing — when software is well tested, arbitrary changes can be made with confidence regardless of the system's age or complexity.

**Lesson.** Fear-frozen code is an existential risk and a hard blocker for codebase-wide progress. The cure is test coverage, not process armor.

## Analogy: Cattle Versus Pets

**Setup.** Distributed-computing folklore distinguishes "pets" (individually named, nursed servers) from "cattle" (interchangeable machines replaced without ceremony). The chapter applies the same analogy to code changes.

**What happened / the point.** A normal handcrafted change is a pet: an engineer spends days or weeks creating, testing, and shepherding it, knows it intimately, and takes pride in landing it — and takes rejection personally. LSC shards must be cattle: nameless, faceless commits that can be rolled back or rejected at any moment (due to a merge conflict or an unforeseen test failure) at negligible cost, because automation regenerates them cheaply. Losing a few cattle is fine unless the entire herd is affected.

**Lesson.** Effective LSC work requires an emotional and operational shift: optimize for cheap regeneration and casual rollback rather than attachment to individual commits.

## Smaller Anecdotes and Notable Details

### The one-billion-line deletion
The largest series of LSCs ever executed at Google removed more than one billion lines of code from the repository over three days, mostly deleting an obsolete section that had already been migrated to a new home. The book poses the rhetorical question: how confident in your tests and tooling do you have to be to delete a billion lines of code?

### Changes the LSC committee rejected
Google's LSC oversight committee has been historically liberal with approvals. The only outright rejections were changes deemed dangerous — such as blanket conversion of every `NULL` to `nullptr` in C++ — or extremely low value, such as converting British spelling to American spelling (or vice versa). The committee also declines cleanups that cannot prevent recurrence, like fixing a common typo with no mechanism to stop it from coming back, and the tooling is deliberately not to be used to fight over "gray" versus "grey" in comments.

### Go added refactoring-friendly features
The chapter notes that the Go language introduced type-alias-style features specifically to support large-scale refactorings, illustrating that language design can deliberately enable non-atomic migrations.

### The "formal Fridays" unfunded mandate
To explain "unfunded mandates," the chapter jokes about a CEO declaring that everyone must wear an evening gown for "formal Fridays" without a raise to pay for the formal wear — a requirement imposed by an external authority with no compensating resources. Telling every product team to migrate itself off an old system is the engineering equivalent.

### clang-format's origin
A footnote notes that the need for machine-generated changes to look human-written was the reasoning behind the original work on clang-format for C++, underscoring how central automatic formatting is to LSC acceptance.

### Plastic six-pack rings
On cleanup: the systems teams most want to let "organically disappear" after a migration are precisely the ones most resistant to disappearing — "the plastic six-pack rings of the code ecosystem." Hence the need for active prevention of new uses (Google uses the Tricorder static-analysis framework to flag new references to deprecated things at review time).
