# Chapter 5: Information Hiding (and Leakage)

## Central idea

Information hiding is one of the most important techniques for making modules deep: each module should encapsulate a few pieces of knowledge (design decisions) inside its implementation so they never appear in its interface. The opposite, information leakage — the same design decision reflected in multiple modules — is one of the most important red flags in software design, because it couples modules so that one change forces edits in many places.

## Key concepts

- **Information hiding** (from David Parnas's 1972 paper "On the Criteria to Be Used in Decomposing Systems into Modules"): each module encapsulates a few pieces of knowledge representing design decisions. The knowledge lives in the implementation and is invisible in the interface. Hidden information can be data structures and algorithms (how to store a B-tree, how to implement TCP, how to parse JSON), low-level details (page size, mapping logical file blocks to physical disk blocks), or high-level abstract assumptions (e.g., "most files are small").
- **Why it reduces complexity, two ways:** (1) It simplifies the interface — the interface presents a simpler, more abstract view and hides details, lowering cognitive load (a B-tree user need not know about fanout or rebalancing). (2) It makes evolution easier — if information is hidden, nothing outside the module depends on it, so a design change touches only that one module (a TCP congestion-control change affects only the protocol implementation, not callers).
- **`private` is not information hiding.** Declaring fields private prevents direct access, but exposing them through getters and setters makes their nature and usage just as exposed as if they were public. Hiding is about knowledge, not access modifiers.
- **The best form of information hiding is total**: the information is completely hidden within the module, so it is irrelevant and invisible to the module's users. But **partial information hiding** still has value: if a piece of information is needed by only a few callers and is accessed through separate methods invisible in common use cases, it is mostly hidden and creates fewer dependencies than information visible to every user.
- **Information leakage**: a design decision reflected in multiple modules, creating a dependency among them — any change to the decision requires changing every module involved. Anything in an interface is leaked by definition, so simpler interfaces correlate with better hiding. **Back-door leakage** happens with no interface exposure at all (e.g., two classes that both understand a file format); it is more pernicious than interface leakage because it is not obvious.
- **Temporal decomposition**: structuring a system to mirror the time order in which operations execute (read-then-modify-then-write becomes three classes). It is a common cause of leakage, because most design decisions (like a file format) manifest at several different times in the application's life, so order-based structure encodes the same knowledge in multiple places. The trap is easy to fall into because execution order is what's on your mind while coding.
- **Overexposure**: an API for a commonly used feature that forces users to learn about rarely used features, raising cognitive load on users who don't need them.

## Actionable principles

- When designing a new module, ask explicitly what knowledge can be hidden inside it. The more you can hide, the more you can simplify the interface, and the deeper the module becomes.
- **Focus module boundaries on the knowledge needed for each task, not the order in which tasks occur.** Order usually matters and will be reflected somewhere in the code, but it must not drive module structure unless the stages genuinely use different information. Temporal decomposition yields shallow modules as well as leakage. The positive procedure: identify the different pieces of knowledge needed to carry out the application's tasks, and design each module to encapsulate one or a few of them — this produces a clean, simple design with deep modules.
- Cultivate a high level of sensitivity to information leakage — Ousterhout calls this one of the best skills you can learn as a software designer. When you find leakage, ask: "How can I reorganize these classes so that this particular piece of knowledge only affects a single class?" Two fixes: (1) if the affected classes are small and closely tied to the leaked information, merge them into one class; (2) pull the knowledge out into a new class that encapsulates just that information — but only if you can find a simple interface that abstracts away the details. If the new class exposes most of the knowledge through its interface, you've merely converted back-door leakage into interface leakage and gained nothing.
- **Information hiding can often be improved by making a class slightly larger.** Two reasons: bringing all code for one capability together (e.g., everything that understands HTTP request format), and raising the level of the interface (one method that performs an entire computation instead of separate methods for each of its three steps).
- Avoid exposing internal data structures through return values. Returning a reference to an internal Map exposes the representation, forces all callers to change when the representation changes (which it often does, e.g., for performance), makes callers do extra work, and risks callers mutating internal state. Provide purpose-built accessors instead (e.g., `getParameter(name)` rather than `getParams()` returning the whole map).
- Push useful transformations down into the module: hide encodings, format distinctions, and type conversions so callers receive data in the form they want (e.g., a `getIntParameter` that does string-to-int conversion internally).
- Provide sensible defaults so the common case is as simple as possible. Defaults are partial information hiding: in the normal case the caller need not even know the defaulted item exists; rare overriders invoke a special method. If the module can compute a value itself (like matching a response's protocol version to the request), requiring the caller to supply it just leaks knowledge into the caller.
- Whenever possible, classes should "do the right thing" without being asked. The best features are the ones you get without even knowing they exist (e.g., I/O buffering should be automatic, never an explicit opt-in as in Java's `BufferedInputStream`).
- Apply information hiding inside classes too: design private methods so each encapsulates some information or capability and hides it from the rest of the class, and minimize the number of places each instance variable is used — fewer usage sites means fewer intra-class dependencies and less complexity.

## Nuances and counterpoints

- **Taking it too far:** information hiding only makes sense when the information is not needed outside the module. If callers genuinely need it — e.g., performance-critical configuration parameters that different uses must tune differently — you must expose it in the interface. The goal is to *minimize* the information needed outside a module (a module that auto-tunes its configuration beats one that exposes knobs), but you must recognize which information truly is needed outside and make sure it is exposed.
- **Against the "many small classes" instinct:** the most common student mistake was dividing code into a large number of shallow classes, which led to information leakage between them. Deliberately making a class slightly larger often improves hiding and deepens the module. This too has a limit — a single class for an entire application is overcorrection; Chapter 9 covers when splitting is justified.
- **Deep modules and information hiding are two views of the same property.** A module that hides a lot of information tends to have more functionality behind a smaller interface (deep); a module that hides little either does little or has a complex interface (shallow either way).

## Red flags

- **Information Leakage** (explicit box): the same knowledge is used in multiple places, such as two classes that both understand the format of a particular type of file.
- **Temporal Decomposition** (explicit box): execution order is reflected in code structure — operations that happen at different times live in different methods or classes. Knowledge used at multiple points in execution gets encoded in multiple places, causing leakage.
- **Overexposure** (explicit box): the API for a commonly used feature forces users to learn about rarely used features, raising cognitive load on users who don't need them.
- Implicit: getters/setters that expose a private field's nature and usage as if it were public.
- Implicit: methods that return references to internal data structures (callers depend on the representation and can corrupt internal state).
- Implicit: callers required to invoke multiple methods, in a particular order, to accomplish one logical operation.
- Implicit: callers required to supply values the module could determine itself (missing or inadequate defaults).
